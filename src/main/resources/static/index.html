지금 직접 걸어보기

이 페이지가 브라우저에서 직접 주문 API를 호출합니다. 재고를 초기화하고 동시에 여러 건을 쏘면, 성공은 재고 수만큼만 나오고 나머지는 409로 떨어집니다.

–202 RESERVED
예약 성공
–409 sold-out
재고 소진, 즉시 응답
–409 duplicate-user
같은 유저 중복
–5xx / 네트워크 오류
–p50 (브라우저 왕복)
–p99 (브라우저 왕복)

      
데모 상품 ID는 9001로, 부하 테스트가 쓰는 상품과 분리돼 있습니다. 브라우저에서 쏘는 것이라 여기 찍히는 지연에는 네트워크 왕복이 포함됩니다 — 서버 내부 지연은 아래 k6 실측 표를 보세요.

    

  






  

    
구조

    
핫패스는 Redis Lua 스크립트 한 번(확인 + 차감 + 중복 체크 + 예약 기록)으로 끝내고, 결제·DB 적재 같은 무거운 일은 아웃박스 → Kafka로 떼어냈습니다.

    


client ─▶ Traefik ─▶ [flashgate-api ×2]   Kotlin · Spring Boot · 가상 스레드
                          │  POST /api/orders  { productId, userId } + Idempotency-Key
                          │
                          ▼  EVALSHA reserve.lua   재고 확인 + 차감 + 유저 중복 체크 + 예약 기록 = 1 round-trip
                    [Redis  master + replica×2 + sentinel×3]
                          │  성공하면 같은 트랜잭션에서 outbox INSERT → 202 { orderId, status: RESERVED }
                          ▼
                    [Kafka] order.reserved  ◀── outbox relay (100ms 폴링, SKIP LOCKED)
                          │
                          ▼
                    [확정 컨슈머]  결제 모의 승인 → MySQL orders 적재 → order.confirmed
                          │        실패하면 compensate.lua 로 재고 복원 + order.cancelled
                          ▼
                    GET /api/orders/{id}  →  RESERVED | CONFIRMED | CANCELLED

      
    
        
  • 왜 Lua인가 — 확인·차감·기록을 한 번의 라운드트립으로 원자화해 락 없이 정확합니다. 대안(DB 행 락, Redisson 분산락)을 같은 부하로 실측해 비교했습니다.
    • 
        
  • 중복 주문 방어 3중 — Lua 안의 유저 중복 체크, Idempotency-Key(Redis SETNX, TTL 24h), 컨슈머의 유니크 제약.
    • 
        
  • 재고 정합 — 트랜잭셔널 아웃박스(at-least-once) + 실패 시 보상 + 1분마다 초기 재고 = Redis 잔여 + 확정 + 취소 대사, 어긋나면 메트릭 알람.
    • 
        
  • 장애 대응 — Sentinel 자동 failover, Resilience4j Retry + CircuitBreaker. 서킷이 열린 동안은 큐잉 대신 503 + Retry-After로 빠르게 실패시켜 지연 폭증을 막습니다.
    •
